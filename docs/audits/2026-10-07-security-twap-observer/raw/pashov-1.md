code_smells: `_openWindow` reads `referenceTick` (head word 3 of `getPoolState`). The hook's `_updateVolatility` (FactoryHook.sol:733) rewrites that value in every `beforeSwap`, nested swaps included. IHookObserver says that a funded observer can run a nested swap. Suppose an observer bound before WthCorrector swaps the same pool inside its `onAfterSwap`. That nested swap's own notification runs a full correction while `LOCK_TSLOT` is 0, and the lock clears at the end of it. The outer notification then runs a second correction. It takes the direction from the user's `delta`, `post` from the current `getSlot0`, and `referenceTick` from the pre-swap tick of the inner executor's last leg. Example: the user moves tick 1000 to 0, the nested swap moves 0 to 2000, and the inner correction returns to about tick 1. The outer band is then about (tick 1, tick 1999). That band goes past the user's pre-swap price (tick 1000), so in-band executor legs pay only the floor fee across ticks the user's swap did not open.
description: An earlier observer that swaps the same pool changes referenceTick, so _openWindow builds the band from that swap, not from the user swap. We did not prove an executor gain or an LP loss with numbers.
